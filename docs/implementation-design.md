# Model Dispatch 实现方案

日期：2026-09-09。状态：设计与实施验收依据；不代表下列功能均已实现。

## 1. 产品目标

轻量 macOS 菜单栏工具，用稳定入口调度第三方本地模型服务。新增平台通过外置配置或插件接入，自动识别安装位置、版本、模型和已有运行配置。用户选择模型即可启动合适的运行版本；API 调用走同一调度流程。

主要职责是发现、导入、调度、观察和提供建议。第三方负责推理、KV 实现、量化、模型格式和更新。宿主不自动修改第三方源码，不自动合并 Git，不自动安装或执行未知仓库。

成功标准：更新引擎后通常无需更改宿主；接口变更只影响对应插件；切换主线/支线通过运行配置完成；现有 Agent 可逐步迁移，原服务可回退。

## 3. 复用优先的技术决策

先冻结自研调度核心扩张，用固定版本现成软件跑隔离验收，再选择生产底座。

| 候选 | 用途 | 必须验证 |
|---|---|---|
| mostlygeek/llama-swap | 优先候选：代理、排队、进程生命周期、TTL、分组、指标 | 常驻服务内部切换、外部进程所有权、取消、队列公平性 |
| AdityaVG13/Model-Switchboard | 菜单栏/运行配置参考 | 是否可扩展任意运行命令、许可证、代码与发布维护状态 |
| lucasmullikin/ModelStatus | 服务探测和菜单栏观察参考 | 探测是否只读、通用 API 覆盖、许可证与维护成本 |
| 当前 Swift 壳 | 已有本机界面 | 若复用外部界面成本更高，保留此薄壳 |

选型门槛：用两个假后端验证完整生命周期，其中一个模拟常驻多模型服务。验证同服务切换不误杀整个服务、跨服务先释放后加载、断开取消、加载失败、流式结束、外部已运行实例、退出与恢复。

若 llama-swap 可直接配置满足，采用其发行二进制和生成配置；若需少量稳定 HTTP 生命周期适配，只增加对应适配器。若必须复刻第二套排队/卸载状态机才能使用，则记录失败用例，保留现有核心。禁止两个调度核心同时争夺同一进程。

暂不决定替换正在使用的核心。旧评估保留为历史证据，追加新评估，不抹去已有发现。复用前检查 LICENSE、锁定版本与校验值，保留第三方声明。

## 4. 分层与实体

调用链：Agent → 统一 API → 唯一调度执行者 → 第三方服务。

菜单栏、CLI 和自动请求都使用同一管理 API。插件发现和配置导入属于控制层，不进入 token 转发热路径。

| 实体 | 示例 | 职责 |
|---|---|---|
| 平台插件 | ds4、mlx-serve、mtplx | 描述发现、解析、版本兼容和操作契约 |
| 安装实例 | ~/Developer/ds4 | 记录仓库/二进制/安装包路径及版本 |
| 运行版本 | DS4 main、Qwen PR991 | 明确 executable、cwd、版本和能力 |
| 服务实例 | ds4-router:8888 | 唯一生命周期所有者和端口 |
| 模型映射 | qwen-flash | 稳定公共 ID → 后端模型及运行版本 |
| 运行方案 | 默认、实验候选 | 用户明确选择的模型与运行版本组合 |

Git 分支不等于已构建的可执行文件。发现分支只能登记候选；必须确认二进制路径和构建来源后才可选用。若多个分支共用一个 checkout，不自动 checkout；可分别使用已有 worktree。调度器不负责创建或合并分支。

同一模型可对应多个运行版本，但公共 ID 必须唯一。实验别名和默认别名分开；验证通过后用户再选择默认指向。服务更新不隐式切换模型变体或支线。

## 5. 插件契约

优先声明式 manifest，首版无需动态加载 Python/JS 插件。对于无法声明式解析的平台，由受审查的内置 reader 扩展，避免把 YAML 变成任意代码执行入口。

建议外置目录：~/Library/Application Support/InferenceDock/plugins/。
插件版本和用户配置分开保存；打包更新不能覆盖用户安装路径或模型选择。

```yaml
schema_version: 1
id: mtplx
display_name: MTPLX
discover:
  executables: ["~/.mtplx/bin/mtplx", "mtplx"]
  version_args: ["--version"]
  config_readers: [mtplx_local]
service:
  mode: managed
  service_key: mtplx-generation
  health_path: /health
  protocol: openai-chat
models_source: discovered
```

此示例是拟议 schema，目前不能直接交给现有 load_config。

操作契约包含：探测健康、列模型、启动、选择模型、取消、卸载模型、停止自有服务。每项明确是否支持、超时、成功条件和版本范围。不支持的操作在界面禁用，不能假装成功。

managed 使用 executable + argv，不执行 shell 字符串。launchd 通过受限平台实现处理明确 label；不得引入任意 stop shell。HTTP 操作限定登记的 loopback 地址与路径，不接受模型元数据提供的任意 URL。

external 仅代理/读取；observe 不具有 load/unload/stop 权限。接管现有服务必须是明确迁移动作，同 endpoint/service_key 不能有两个生命周期所有者。

一个 MTPLX service_key 配多模型启动参数，替代当前五个同端口 managed adapter。切换时等待旧进程完全退出；启动前检查端口归属，不能把其他进程的 health 当成自己的启动成功。

插件更新先校验并展示变更；新加入执行动作或权限时不能静默启用。模型文件、README 和仓库中的说明只作为数据，不作为可执行指令。

## 6. 安装与配置发现

扫描范围依次为：已登记路径、PATH、已知应用目录、用户选定的 Developer 根目录。限制递归深度和文件大小，不全盘扫描。不得因为路径名称包含模型名就判定兼容。

数据源包括：安全读取的 JSON/YAML/TOML/plist、git worktree/HEAD/remote 元数据、进程 argv、受支持的 health/models GET。只执行已识别可信程序的 version/help；不执行仓库脚本，不 source .zshrc。

导入流程：发现 → 解析 → 显示来源与冲突 → 生成预览 → 保存宿主映射 → 只读复核。凭据不导入明文，采用 Keychain/凭据引用；显示 remote 时移除 URL 内认证信息。

每个字段记录 value、source、observed_at、confidence、scope。scope 区分模型宣称上限、配置值、当前运行值与测试值。例如 config 声称 512K 但 argv 为 256K，界面显示差异，不能自动任选其一。

已有配置是默认导入基线。宿主只保存调度参数和必要引用，不复制所有后端设置。后端更改后增量扫描，按字段展示漂移；用户覆盖值不能被自动发现覆盖。缺失、不支持和未知要区分。

配置至少包括：二进制/模型路径、公开与后端模型 ID、context、max output、视觉组件、思考协议、并发、缓存路径/预算、SSD streaming、辅助模型、现有 idle 策略。读取不到时标未知。

## 7. 配置与升级治理

优先级：用户显式覆盖 → 已确认导入配置 → 插件默认值。运行观测是证据，不直接写回配置。生成配置是可重建产物，不成为另一份人工配置源。

保存时原子写入，保留上一份可回退宿主配置，并验证公开 ID、端点、所有权、端口和模型路径。配置文件内秘密信息不进入日志或 Git。

第三方更新后重新探测版本及能力；已知兼容范围内可继续，能力消失则禁用对应动作并提示。运行中的服务保持原快照，新版本用于下一次安全加载。二进制替换与 Git 合并由各平台自己的维护流程完成。

宿主、插件、运行版本和模型工件分别记录版本。不得把“包含 upstream main”显示为“支线已合并进入官方 main”。不存在的路径保留为离线记录，不自动删除配置。

## 8. 调度、取消与内存

### 8.1 常驻、管理权限与互斥分别设置

三个维度独立：ownership 决定能否操作服务；keep_running 决定宿主是否因空闲退出服务；exclusive_group 决定与谁互斥。常驻服务不等于所有模型永久驻留，内部模型 idle 策略继续由后端管理。

| 服务 | 初始管理方式 | 互斥名单 | 常驻规则 |
|---|---|---|---|
| oMLX | observe | 排除 | 不启动、不停止、不卸载，保留 RAG 功能 |
| Ollama（若接入） | 默认 observe/external | 默认排除，可调整 | 保持现有服务，模型驻留沿用其配置 |
| DS4/MLX-Serve/MTPLX 生成模型 | 逐步按实例接管 | 默认 large-local | 仅对已接管范围执行切换和 idle |

互斥采用显式加入名单，未分组实例不因其他组切换被停止。用户可以选择“不参与互斥”、加入指定组或只观察。组应约束被管理的模型资源，不要求所有常驻轻量网关退出；服务可继续运行而卸载其重模型。

不参与互斥的实例仍消耗整机资源，不能视为零成本。资源紧张只排队/拒绝新的受管理加载，绝不扩大停止范围。排除互斥也不代表取消该服务自己的并发或内存限制。

此为目标行为，当前 MVP 单组容量 1 的实现尚不支持完整的独立分组/排除控制；上线前需通过“常驻服务 + 互斥组切换”的测试，不能只在 UI 增加开关。

首版默认受管理的大模型串行切换。oMLX 保持 observe，RAG 等外部负载作为资源余量，不被停止。后续仅对实测可并存的组合开放并发，不能把 capacity=2 当成内存安全保证。

状态：unloaded → loading → ready/busy → draining → unloading；异常进入 failed/unknown。未知状态禁止叠加加载。使用租约/活动请求计数处理自动调用、菜单操作和空闲卸载竞争。

停止输出、卸载模型、停止服务是三种不同操作。客户端断开先取消该请求，不伤害其他请求。空闲计时自最后一次请求结束计算；加载与排队期间不卸载。绕过统一入口的活动必须通过后端可靠状态观察；无法确认时不强制抢占。

模型权重驻留、Metal wired 内存、RSS、SSD KV 和 OS 文件缓存分开记录。宿主不模拟后端释放策略，不承诺请求结束后 wired 内存必然立即下降，也不跨引擎共用 KV 文件。

启动前资源判断使用机器内存、压力/交换增量、实测峰值与安全余量。缺少可靠估算时提示未知并采用保守串行策略；不能仅按模型文件大小判断。主动性能测试需要空闲窗口，不能打断用户调用。

## 9. 推荐与测试

推荐是有来源、可撤销的候选：官方默认优先，机器实测其次。记录机器芯片/内存、版本、模型工件、ctx、KV/MTP/SSD 参数及样本数。不能宣称某组参数在所有负载下“最佳”。

首版推荐只覆盖上下文余量、并发度、超时、缓存磁盘预算及是否应采用后端支持的 SSD streaming。任何推荐应用都展示具体字段差异；大部分第三方高级参数仍由原工具管理。

测试分三级：

1. 被动日常观测：请求耗时、排队、错误、结束原因、usage、TTFT 和可用后端指标。
2. 手动快速检查：健康、短文本、SSE、工具调用、图片（仅宣称支持者）、取消、卸载。
3. 空闲窗口对比：同模型/量化/模板及固定请求、长前缀、小增量、多轮工具，重复 A/B。

长上下文梯度从 4K、16K、32K 开始，通过资源门槛再测试 64K/128K。测试上限由实际运行配置与机器余量决定，不自动把模型最大窗口全部填满。每次只运行一个候选并设置耗时、输出和内存压力停止条件。

同模型跨引擎比较必须记录量化、模板、思考、图片、辅助权重和实际 token 数的差异；不满足等价时只称“当前配置端到端比较”。速度不能证明质量，质量测试另含结构化输出、工具参数、中文/代码任务及正确性断言。

指标定义：TTFT 为请求发出至首个有效内容/思考增量；正文首 token 另记。排队、冷加载与 prefill 不混为一个速度。仅当后端给出真实 prefill token/time 才报告 prefill t/s。缓存命中只解释对应后端明确字段，不把累计 R/W 当单轮数据。缺指标显示未知。

日志默认不存提示词、图片、工具输出或密钥；保存版本标识、计时、计数、状态及脱敏错误。近期原始记录按容量轮转，日汇总可保留更久；本地保存并支持导出。通过其他端口的请求标明观测不完整。

## 10. 菜单栏与设置

菜单只显示活动服务/模型、阶段、最近速度、快速切换、取消、卸载、打开原生界面。详细内容放设置窗口：

- 安装：路径、版本、分支/worktree、可执行文件及离线状态。
- 模型：运行版本选择、上下文/能力来源、默认别名。
- 服务：所有权、互斥规则、已有配置位置、健康与日志。
- 检查：漂移、兼容性、推荐与最近测试。
- 历史：按模型和运行版本查看 TTFT、prefill、decode、缓存和失败趋势。

退出界面默认保持核心及活动任务；停止全部是显式操作。当前实现的菜单退出行为与此目标不同，需要单独迁移并验证进程所有权。避免 core 遗留导致新配置不生效；启动校验配置版本，不能通过杀未知端口进程解决。

| 阶段 | 工作 | 验收/交付 |
|---|---|---|
| A 现状固化 | 服务清单、文档纠错、现有入口/所有权核实 | 基线报告；无需改现有服务 |

| D 生命周期接入 | 在选定核心上实现唯一所有权和最薄适配 | 同服务/跨服务切换、取消、失败恢复、端口冲突测试 |
| E 观测与检查 | 指标归一、日常历史、快速检查与限定对比 | 指标可追溯；缺失不伪造；测试可取消 |

每阶段单独本地提交和验收记录。实现可交给已授权的 K3-256K/Luna Max，审查与实现分开；主负责人验收。先完成 B 再决定 D 的核心代码，不同时维护两套生产状态机。

交付文件：插件 schema 和示例、发现/导入结果、运行配置映射、复用决策、测试报告、运维和故障命令、版本兼容记录。实现命令按最终核心确定，不在设计阶段宣称未实现 CLI 已可运行。

## 12. 回退与最终门槛

迁移不删除现有二进制、模型、缓存、plist 或 Agent 配置。接管时先停止旧所有者的对应控制职责，避免重叠；保留恢复步骤，失败立即恢复原入口。跨引擎共享模型文件须符合各自格式契约，缓存始终由引擎拥有。

上线必须证明：oMLX 未受影响；无双重大模型误加载；忙时切换不截断请求；断开取消不伤其他请求；错误/SSE 正常传达；冷启动失败可恢复；安装发现不执行未知代码；秘密不写日志；菜单重启不重复启动；主线/支线选择正确；旧入口可回退。

首版不做自动 Git 合并、自动下载所有模型、自动寻找并运行任意仓库、无人值守压力测试或复杂内存装箱。未来增加平台以 manifest/reader 为单位，不复制推理引擎。
